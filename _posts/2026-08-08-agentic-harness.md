## 작업 이후 남아야 할 것 {#question}

AI 에이전트를 개발에 사용하면서 가장 먼저 흐려진 것은 작업의 소유권과 완료 기준이었습니다. Claude가 백엔드·프론트엔드·모바일 에이전트에 일을 나눠도 대화창에는 최종 결과가 중심으로 남았습니다. 개발이 한창 바쁠 때는 어떤 명령이 전달됐고, 누가 실행 중이며, 무엇이 완료되거나 실패했는지 다시 대화를 따라가야 했습니다.

그래서 두 가지를 함께 만들었습니다. Claude는 중앙에서 작업을 나누고 결과를 종합하며, 역할별 에이전트는 담당 영역의 구현과 지식을 축적합니다. 사람은 관제판에서 실제 로그에 남은 위임·실행·완료 흐름을 한눈에 확인합니다.

목적은 에이전트를 많이 실행하는 것이 아니었습니다. **지금 누가 무엇을 하는지 보이게 만들고, 작업이 끝난 뒤에는 다음 판단에 사용할 전문성이 남게 하는 것**이었습니다.

## 역할과 소유권 {#fixed-roles}

구현 역할을 `backend`, `frontend`, `mobile`, `devops` 네 가지로 고정했습니다. 작업마다 새로운 이름의 에이전트를 만드는 대신 저장소와 기술 영역에 따라 책임을 분리했습니다.

오케스트레이터는 사용자와 대화하고 일을 나누며 결과를 통합합니다. 구현은 해당 저장소의 규칙과 도메인 지식을 가진 역할이 담당합니다. 목적은 오케스트레이터의 토큰을 아끼는 것이 아니라 실제 작업을 통해 각 역할의 전문성이 깊어지게 만드는 것이었습니다.

## 판단 기준을 남기는 방식 {#durable-knowledge}

세션이 끝나면 작업 중 확인한 판단 근거도 함께 사라집니다. 다음 작업에서 같은 사실을 다시 조사하지 않도록, 반복해서 적용할 수 있는 규칙을 해당 저장소의 `CLAUDE.md`, `AGENTS.md`, Serena 메모리에 기록하게 했습니다.

모든 정보를 저장하지는 않습니다. 한 번의 작업 상태나 금방 바뀔 구현 세부사항이 아니라 다음 작업의 판단을 실제로 바꾸는 안정적인 규칙만 남깁니다.

```yaml
roles:
  - backend
  - frontend
  - mobile
  - devops
review:
  owner: codex
  trigger: explicit-request
knowledge:
  write_back: owning-repository
```

지식의 소유 위치도 구분했습니다. 팀 운영 규칙은 루트 저장소에, 백엔드의 테넌트 검증 규칙은 백엔드 저장소에, 블로그의 편집 원칙은 블로그 저장소에 둡니다. 도메인 지식이 중앙 문서 하나에 섞이지 않도록 했습니다.

## 구현과 리뷰의 분리 {#independent-review}

구현한 에이전트가 같은 추론과 가정을 가진 채 자기 코드를 검토하면 놓친 전제를 다시 놓칠 수 있습니다. 구현 역할과 별도로 Codex 리뷰 레인을 두고, 완료된 결과를 새로운 컨텍스트에서 확인하게 했습니다.

리뷰는 자동 반복하지 않습니다. 사용자가 명시적으로 요청했을 때 한 번 수행하고, 수정 후 다시 검토하려면 새 승인을 받습니다. 품질 루프가 사람의 통제 없이 계속 실행되는 것을 막기 위한 경계입니다.

보안, 법률·저작권, 비용 효율도 별도 검토 관점으로 분리했습니다. 인증과 시크릿, 외부 이미지와 폰트, CDN·스토리지 전송량처럼 구현 정확성만으로 판단하기 어려운 문제를 각 관점에서 확인합니다.

## 에이전트 관제판 {#passive-observation}

관제판은 에이전트가 자신의 상태를 별도 API로 보고하는 방식이 아닙니다. Kotlin·Spring WebFlux 백엔드가 Claude Code의 로컬 JSONL 로그를 읽고, 위임 시작·에이전트 출력·완료·실패·도구 실행을 공통 이벤트로 변환합니다. 현재 상태와 대화 흐름은 SSE로 Vue 프론트에 전달합니다.

화면은 사용자→Claude→역할별 에이전트의 구조를 먼저 보여줍니다. 그 아래에서는 Claude가 어떤 역할에 작업을 위임했는지, 각 역할이 실행 중인지 완료·실패했는지, 어떤 출력이 오갔는지를 역할별로 분리해 볼 수 있습니다. 모든 메시지를 하나의 타임라인에 섞지 않아 중앙에서 전체 작업을 관제하기 쉬웠습니다.

실시간 작업 상태는 메모리와 SSE로 가볍게 다루고, 다시 확인해야 하는 회의록은 MySQL에 보관했습니다. 지금 일어나는 일과 나중에 참고할 기록의 수명주기를 분리한 것입니다.

이 화면은 개발이 가장 바쁠 때 실제로 활용했습니다. 여러 저장소의 작업을 동시에 진행할 때 대화창을 다시 훑지 않고도 Claude가 어느 역할에 일을 넘겼는지, 완료 보고가 돌아왔는지, 실패하거나 오래 멈춘 작업이 있는지 확인할 수 있었습니다.

다만 에이전트의 모든 사고와 통신이 보이는 것은 아닙니다. 관제판은 오케스트레이터 로그에 기록된 명령과 결과를 읽습니다. 서브에이전트의 내부 과정이 로그로 전달되지 않았다면 화면에도 나타나지 않습니다. 따라서 전체 사고 과정을 재현하는 도구가 아니라, 실제로 관찰 가능한 실행 흐름을 중앙에서 확인하는 도구로 범위를 정했습니다.

## 한계와 적용 조건 {#adoption}

이 구조를 만들면서 얻은 기준은 “더 많은 에이전트를 쓰는가”가 아니었습니다.

- 역할과 작업 범위가 명확한가
- 결과를 어떤 검증으로 완료라고 판단하는가
- 재사용 가능한 지식이 올바른 저장소에 남는가
- 구현과 검토가 같은 가정에 갇히지 않는가
- 사람이 현재 상황을 보고 개입할 수 있는가

에이전트의 숫자보다 작업을 추적하고 판단을 축적할 수 있는 구조가 먼저였습니다. Claude는 모든 일을 혼자 실행하기보다 역할별 에이전트를 지휘하고 결과를 종합했습니다. 사람은 관제판으로 그 흐름을 확인하고, 승인과 우선순위 판단이 필요한 지점에 개입했습니다.

이 방식은 저장소별 규칙이 있고 역할 간 소유권을 나눌 만큼 작업이 지속될 때 효과가 있습니다. 짧은 일회성 작업에서는 문서화와 조율 비용이 더 클 수 있습니다. 앞으로도 에이전트를 추가하는 기준은 동시 실행 가능 여부가 아니라, 독립된 책임과 검증 방식, 축적할 전문 지식이 있는지로 판단합니다.
