백엔드, PC 웹, 모바일 웹을 별도 저장소로 운영하면서도 배포는 한 흐름에 가깝게 다루고 있었습니다. 한 영역의 수정이 다른 영역의 배포와 얽히면 작은 오류를 고친 뒤에도 확인하고 반영하는 과정이 길어졌습니다.

그래서 저장소마다 독립된 Jenkins 파이프라인을 두었습니다. 변경된 애플리케이션만 빌드하고 배포할 수 있게 하자 운영 중 발견한 오류와 화면 개선도 필요한 영역에 바로 반영할 수 있었습니다.

> **판단 기준 / One Perspective** — 저장소가 나뉘어 있다면 배포 단위도 나누고, 공통 규칙은 각 파이프라인에 같은 기준으로 적용한다.

## 배포 단위 분리 {#problem}

세 애플리케이션은 변경 주기가 달랐습니다. 백엔드 수정 없이 PC 화면만 바꾸거나, 모바일 사용 흐름만 개선하는 경우도 있었습니다. 이를 함께 배포할 이유는 없었습니다.

배포 단위를 저장소와 맞추면서 각 영역이 자신의 검증과 이미지 빌드, 운영 반영을 맡도록 했습니다. 하나의 거대한 파이프라인을 만드는 대신, 같은 배포 순서를 세 저장소가 공유하도록 구성했습니다.

## 세 개의 파이프라인 {#pipeline}

<div class="mermaid">
flowchart LR
  B[백엔드 저장소] --> BP[백엔드 배포]
  P[PC 웹 저장소] --> PP[PC 웹 배포]
  M[모바일 웹 저장소] --> MP[모바일 웹 배포]

  BP --> R[컨테이너 레지스트리]
  PP --> R
  MP --> R
  R --> S[운영 서버]
</div>

각 파이프라인은 `검증 → 이미지 빌드 → 레지스트리 저장 → 운영 서버 반영` 순서를 따릅니다. NCP의 컨테이너 레지스트리를 이미지 전달 지점으로 두어, Jenkins에서 만든 이미지와 운영 서버에서 실행할 이미지를 같은 태그로 연결했습니다.

백엔드와 두 프론트엔드의 빌드 방식은 다르지만 배포 흐름은 같게 유지했습니다. 한 파이프라인에서 확인한 수정 사항은 나머지 저장소에도 같은 운영 규칙으로 반영했습니다.

## 운영 중 만난 문제 {#challenges}

첫 번째는 자격 증명이었습니다. 레지스트리 계정, 운영 서버 SSH 키, 애플리케이션의 실행 비밀값을 코드에 넣지 않고 Jenkins Credentials에서 관리했습니다. 파이프라인에는 실제 값 대신 필요한 자격 증명의 식별자만 남기고, 빌드와 배포 시점에만 주입했습니다.

두 번째는 디스크였습니다. 배포할 때마다 Docker 이미지가 쌓이면서 운영 서버의 사용량이 계속 늘었습니다. 사용하지 않는 이미지를 정리하고, 이후에는 Docker 데이터가 사용할 공간을 별도 볼륨으로 옮겼습니다. 구현 자체는 복잡하지 않았지만, 배포 자동화에는 새 이미지를 올리는 과정뿐 아니라 반복 배포가 남기는 파일을 관리하는 기준도 필요했습니다.

## 달라진 반영 속도 {#result}

파이프라인을 나눈 뒤에는 오류가 발생한 영역만 수정하고 다시 배포할 수 있게 됐습니다. PC 웹의 화면 개선이 백엔드나 모바일 웹의 재배포로 이어지지 않았고, 운영 중 확인한 작은 문제도 이전보다 짧은 흐름으로 반영할 수 있었습니다.

현재 구조는 복잡한 무중단 배포보다 세 애플리케이션의 변경과 배포를 독립시키는 데 초점을 맞췄습니다. 운영하면서 추가된 기준은 자격 증명을 코드 밖에 두는 것과, 이미지 누적이 서버 디스크를 다시 압박하지 않도록 배포 이후의 상태까지 확인하는 것입니다.
