어제와 다음 날처럼 서로 다른 기준일의 재고 수량을 확인하는 API가 필요했습니다. 매일 재고를 집계해 저장하면 조회는 단순해지지만, 이 화면을 위해 상품별 일일 재고를 별도로 유지해야 했습니다.

그래서 별도 집계 테이블을 만들지 않았습니다. 기존 거래 이력에서 요청한 상품의 기준일 재고를 계산하되, 이미 적용된 파티션과 인덱스를 먼저 활용했습니다. 조회 기간을 최대 6개월까지 늘릴 때 남은 지연은 점포코드와 기존 발주 날짜 인덱스로 후보를 한 번 더 줄이는 방식으로 해결했습니다.

> **판단 기준 / One Perspective** — 스냅샷을 새로 저장하기보다, 기존 조회 경로에서 거래 후보를 더 좁힐 조건을 먼저 찾는다.

## 기준일 재고를 조회하는 문제 {#problem}

재고 거래 테이블에는 매입·매출과 재고 이동 과정이 기록됩니다. 기준일 재고 조회는 이 거래에서 특정 점포와 상품의 이력을 찾아 해당 시점의 수량을 계산하는 방식이었습니다.

하루 단위 조회에서는 문제가 크지 않았지만, 조회 범위를 최대 6개월까지 늘리자 탐색해야 할 거래도 많아졌습니다. 문제는 계산식이 아니라, 기준일 수량을 만들기 전에 읽는 후보 범위였습니다.

## 집계 테이블을 만들지 않은 이유 {#choice}

기준일별 재고를 미리 집계하는 방법도 가능했습니다. 그러나 이 API는 상품코드를 기준으로 필요한 상품의 이력을 조회하는 화면을 위한 기능이었습니다. 상품별 일일 재고를 미리 저장하면 조회 한 번은 단순해지지만 디스크 사용량과 집계 운영 비용이 계속 증가합니다.

반면 담배처럼 반복적인 집계와 확인 자체가 업무 요구인 영역은 집계 데이터를 별도로 유지할 이유가 있습니다. 자주 읽는 범위와 정확성 확인 절차가 명확하기 때문입니다. 이번 API는 필요한 상품을 그때 조회하는 기능이었으므로, 거래 이력을 조회하는 기존 방식을 유지했습니다.

집계와 실시간 조회 중 어느 쪽이 항상 낫다는 판단은 아니었습니다. 저장할 대상의 범위와 조회 빈도에 비해 스냅샷 유지 비용을 지불할 이유가 있는지를 기준으로 나눴습니다.

## 확장 전에 확인할 것 {#challenges}

- 기존 조회가 어떤 조건으로 범위를 줄이는지 확인할 것
- 하루 단위였던 조회 범위를 최대 6개월까지 늘릴 것
- INSERT가 계속 발생하는 테이블에 새 인덱스를 추가하지 않고 해결할 것
- 최대 6개월 조회를 API 허용 기준 안에 맞출 것

## 이미 있던 최적화 {#existing}

기존 조회에는 날짜 범위 파티션과 PK, 업무 조회를 위한 인덱스가 이미 적용되어 있었습니다.

점포코드도 각 거래에 들어 있어 별도의 점포 관계를 다시 조회하지 않고 요청 점포를 바로 제한할 수 있었습니다. 점포코드 자체를 비정규화라고 단정하지 않고, 이 조회에서 바로 사용할 수 있는 필터 조건으로 봤습니다.

기존 구조는 다음 범위를 이미 줄이고 있었습니다.

<div class="mermaid diagram-wide">
flowchart LR
  A[재고 거래 이력] --> B[기존 날짜 범위 파티션]
  B --> C[점포코드·상품코드로 대상 제한]
  C --> D[기준일 범위의 거래 집계]
</div>

다만 날짜 범위를 넓히면 해당 점포와 상품의 후보 거래도 함께 늘어났습니다. 기존 최적화만으로 하루 조회는 처리할 수 있었지만, 최대 6개월 조회에는 한 단계가 더 필요했습니다.

## 발주 날짜를 먼저 찾기 {#order-date}

단서는 현재 재고 수량을 계산하던 기존 Repository와 업무 코드에 있었습니다. 관련 거래를 발주 날짜 기준으로 조회하는 경로를 분석하면서, 거래 테이블에 발주 날짜가 미리 저장되어 있고 해당 컬럼에 인덱스가 있다는 사실을 확인했습니다.

발주 날짜는 현재 재고와 관계있는 거래 묶음을 먼저 찾을 수 있는 비정규화된 업무 키였습니다. 기준일 범위 전체를 바로 집계하는 대신, 관련 발주 날짜를 선행 조회한 뒤 그 날짜 목록을 본 조회의 IN 조건으로 전달했습니다.

<div class="mermaid diagram-wide">
flowchart LR
  A[점포·상품·기준일 입력] --> B[관련 발주 날짜 선행 조회]
  B --> C[발주 날짜 목록]
  C --> D[점포코드·상품코드·발주 날짜 IN 조회]
  D --> E[기준일 재고 계산]
</div>

이 순서는 Oracle이 조건을 반드시 이 순서로 실행한다는 뜻이 아닙니다. 기존 데이터 모델에서 어떤 조건으로 후보 집합을 좁힐 수 있는지 분석하고 API를 구성한 순서입니다.

## 인덱스를 추가하지 않은 이유 {#index}

점포·상품·날짜를 묶은 신규 인덱스를 추가하는 방법도 생각할 수 있었습니다. 하지만 대상 테이블에는 재고 이동 거래가 계속 INSERT됩니다. 새 인덱스는 조회 성능뿐 아니라 쓰기의 인덱스 갱신과 저장 공간 비용으로 이어집니다.

이미 날짜 파티션과 PK·업무 인덱스가 있었고, 발주 날짜 컬럼에도 인덱스가 적용되어 있었습니다. 따라서 구조 변경의 비용을 먼저 지불하기보다 기존 발주 날짜 조회를 선행 조건으로 활용했습니다. 기존 설계에 조건 하나를 더 얹어 읽을 범위를 줄인 선택이었습니다.

이는 신규 인덱스를 무조건 피해야 한다는 의미가 아닙니다. 기존 접근 경로로 API 허용 기준을 맞추지 못했다면 실행 계획과 읽기량을 근거로 새 인덱스를 검토했을 것입니다. 이번에는 그 비용을 지불하기 전에 해결 가능한 범위였습니다.

## 검증 결과와 한계 {#verification}

기존 하루 단위 조회를 최대 6개월까지 늘려 검증했고, 점포코드와 발주 날짜로 후보를 줄인 뒤에는 시스템의 API 허용시간과 Slow API 기준 안에서 반환됐습니다. 집계 테이블이나 신규 인덱스 없이 조회 기간을 확장했고, 실제 운영 이후 이 기능과 관련된 CS도 들어오지 않았습니다.

아쉬운 점은 전후 응답시간을 초 단위로 측정하거나 실행 계획과 실제 실행 통계를 별도로 보관하지 않았다는 것입니다. 당시 완료 기준은 최대 6개월 조회가 시스템의 API 허용시간을 넘지 않는 것이었고, 해당 기준을 통과한 시점에 작업을 마무리했습니다.

따라서 PSTART·PSTOP으로 파티션 프루닝을 확인했다거나, 발주 날짜 인덱스가 어떤 방식으로 선택됐고 Buffers가 얼마나 감소했다고 단정하지 않습니다. 직접 확인한 것은 기존 파티션과 인덱스의 존재, 발주 날짜를 사용하는 업무 경로, 최대 6개월 조회가 API 허용 기준을 통과한 결과와 운영 이후 관련 CS가 없었다는 점입니다.

지금 같은 작업을 다시 진행한다면 DBMS_XPLAN.DISPLAY_CURSOR의 실제 실행 통계로 파티션 접근 범위, 선택된 인덱스, 처리 행 수와 Buffers를 전후 비교해 함께 남길 것입니다. 설계 판단과 실행 계획의 증거를 같은 기록에 보관하는 것이 이 경험 이후 추가된 검증 기준입니다.
