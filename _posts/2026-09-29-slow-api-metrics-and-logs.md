개인 SaaS에서 로그인 API의 Slow API 알림을 받았습니다. 로그인 코드나 DB 설정을 바로 바꾸기보다, **서버가 실제로 어느 구간의 지연을 측정했는지**부터 확인했습니다.

HTTP 메트릭으로 애플리케이션 처리 구간의 지연을 확인하고, DB 커넥션·GC·CPU 지표로 우선순위를 낮출 가설을 골랐습니다. 그래도 요청 내부의 시간은 설명되지 않아 기존 로그를 확인했고, 이미 종료한 Tempo로 Trace를 전송하려는 설정 불일치를 발견했습니다. 이 설정을 정리한 뒤 체감 지연과 알림은 사라졌습니다. 다만 전송 실패가 응답 지연의 직접 원인이었는지는 측정하지 못했으므로, **확인한 구성 문제와 지연의 인과관계는 분리**해 기록합니다.

> **판단 기준 / One Perspective** — 각 메트릭이 설명할 수 있는 범위만큼 원인 후보를 줄이고, 남은 요청 내부의 단서는 로그에서 확인한다.

## 알림이 가리킨 구간 {#signal}

[앞서 구축한 모니터링 경로]({{ '/product/raspberry-pi-monitoring-boundary/' | relative_url }})는 HTTP 요청 시간이 기준을 넘으면 URI·Method·상태 코드와 시각을 Slack으로 알립니다. 이 값으로 느린 요청을 찾을 수는 있지만, 브라우저부터 DB까지의 어느 단계가 원인인지는 바로 알 수 없습니다.

Grafana Explore에서 알림 시각과 로그인 요청으로 범위를 좁혔습니다. Spring Boot의 HTTP 요청 시간에도 지연이 기록돼 있어, 브라우저 표시만의 문제로 한정할 수 없었습니다. 반면 이 메트릭은 인증·계정 조회·세션 처리 중 어디서 기다렸는지는 보여주지 않았습니다.

## 메트릭으로 낮춘 가설 {#metrics}

요청 내부를 계측하기 전에 이미 수집하던 지표로 큰 원인 후보를 검토했습니다.

| 확인한 범위 | 관측과 해석 |
| --- | --- |
| DB 커넥션 획득·대기 | 획득은 짧았고 수집 시점의 대기 요청은 없었습니다. 풀 고갈을 우선 원인으로 볼 근거는 부족했습니다. |
| DB 커넥션 사용 | 수 초의 사용 시간이 있었지만 풀 전체의 값이라 느린 로그인 요청과 연결할 수 없었습니다. SQL 병목을 확정하지 않았습니다. |
| JVM GC·메모리 | 장시간 GC 정지나 메모리 급증은 보이지 않았습니다. 이 지표만으로 시스템 전체의 메모리 압박까지 배제할 수는 없습니다. |
| 프로세스 CPU | 같은 시간대에 높은 CPU 사용은 관측되지 않았습니다. 특정 스레드의 짧은 계산이나 디스크 대기까지 설명하는 지표는 아닙니다. |

이 결과는 ‘메트릭이 정상이니 문제가 없다’는 뜻이 아니었습니다. HTTP 처리 시간은 길었고, 지금 본 지표로는 그 시간을 설명하지 못했습니다. 풀 크기나 GC 설정을 먼저 바꾸면 원인을 확인하기 전에 운영 비용만 늘릴 수 있어, 다음 조사는 요청 시간대의 로그로 옮겼습니다.

## 기존 오류 로그의 단서 {#logs}

새 계측을 배포하기 전에 백엔드 컨테이너의 기존 로그를 알림 시간대로 제한해 확인했습니다. 로그인 지연 시각에도 Trace 전송 실패가 반복됐습니다.

```text
Failed to export spans. The request could not be executed.
java.net.UnknownHostException: tempo
```

Tempo는 서버 메모리 부담 때문에 종료했지만, 애플리케이션의 OTLP Trace Exporter는 여전히 수신처를 찾고 있었습니다. 수신 저장소를 끄는 일과 애플리케이션의 전송 설정을 끄는 일은 별도였습니다. 로그는 그 사이의 불일치를 분명히 보여줬습니다.

반대로 이 오류가 로그인 요청 스레드를 직접 멈췄다는 증거는 없었습니다. Trace 전송은 별도 작업 스레드에서 이루어졌고, 이번에는 Span 생성·대기열·반복 오류 로그가 요청 시간에 얼마나 기여했는지 재지 않았습니다. 같은 시각에 오류가 있었다는 사실만으로 병목 위치까지 단정하지 않았습니다.

## 설정 정리와 확인 범위 {#result}

운영 프로파일에서 OTLP Trace Exporter와 더는 사용하지 않는 endpoint를 정리하고, Trace 샘플링을 껐습니다. Prometheus 메트릭 수집은 유지했습니다. 근거가 부족했던 커넥션 풀과 GC 설정은 바꾸지 않았습니다.

재배포 후 로그인과 평소 느리게 느껴졌던 요청들을 다시 사용했고, 초기 관찰에서는 체감 지연과 Slow API 알림이 사라졌습니다. 이는 운영 사용과 알림으로 확인한 경과입니다. 모든 요청의 응답시간 분포를 전후 비교한 결과나 장기간 재발 여부는 아니므로, 설정 불일치 제거를 **검증된 변경**, 지연 소실을 **함께 관측한 결과**로 구분합니다.

## 다음 신호에 남긴 기준 {#next}

이번 조사는 알림에서 시간대를 맞추고 메트릭을 비교한 뒤 오류 로그를 찾는 순서로 진행됐습니다. 메트릭이 가리키는 범위와 로그가 증명하는 범위를 구분했기에 풀·GC를 근거 없이 조정하지 않았습니다. 설정을 정리한 뒤 로그인 지연 체감과 알림이 사라진 결과도 확인했습니다.

다만 요청 하나의 내부 로그를 찾으려면 매번 시간대와 경로를 수작업으로 맞춰야 했습니다. 이후에는 백엔드 로그의 Trace ID를 로컬 ELK에서 검색하고, 요청 완료 요약으로 알림에 해당하는 요청을 좁히도록 연결했습니다.
