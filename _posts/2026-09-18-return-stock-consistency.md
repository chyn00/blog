점포 재고 업무는 오랫동안 POS를 중심으로 운영됐습니다. 차세대 전환에서는 화면과 대부분의 프론트 로직을 Vue로 옮겼습니다. OS 제어나 파일 접근이 필요할 때는 별도로 실행되는 Electron 프로세스와 IPC로 통신했습니다. 같은 재고 업무는 PC 웹·모바일·태블릿으로 확장됐습니다.

기능은 옮겼지만 사용 방식은 달라졌습니다. POS는 업무 중 계속 열려 있었고, 그사이 다른 채널이 실제 재고를 바꿀 수 있었습니다.

사용자는 화면을 열었을 때 본 과거 재고를 기준으로 반품 수량을 입력했습니다. 예를 들어 POS에는 재고가 10개로 보였지만, 모바일 처리 이후 실제 재고는 이미 8개일 수 있었습니다. 이 상태에서 POS의 10개를 기준으로 10개를 반품하면 실제 재고는 -2가 됩니다. 도난이나 오입고·과입고 등으로 실물과 전산 수량이 항상 일치하지 않아 음수 재고를 허용했기 때문에, 오류도 발생하지 않았습니다. 숫자는 상황을 설명하기 위한 예시입니다.

## 운영 신호와 재현 {#signal}

Datadog RUM으로 반품 화면의 조회와 저장 요청을 확인하고, Trace와 DB 데이터로 처리 순서를 맞췄습니다. QA 환경에서는 POS 화면을 새로고침하지 않은 채 다른 채널에서 재고를 변경한 뒤 반품하는 상황을 재현했습니다.

계산식은 정상적이었습니다. 실제 재고 8에서 반품 10을 차감하면 -2가 됩니다. 문제는 계산 결과가 아니라, POS에 남아 있던 10과 처리 시점의 실제 재고 8이 달랐다는 점이었습니다.

## 문제 정의: 오래된 화면 {#problem}

과거 수량으로 DB를 덮어쓴 것은 아닙니다. 사용자는 POS에 남아 있는 재고를 기준으로 판단했고, 서버는 처리 시점의 실제 재고로 계산했습니다. 화면과 서버가 서로 다른 시점의 재고를 보고 있었습니다.

그래서 모든 재고 변경을 잠그는 문제로 정의하지 않았습니다. 오래 열린 POS의 재고와 처리 시점의 실제 재고가 달라졌는지 반품 전에 감지하는 문제로 좁혔습니다.

> **판단 기준 / One Perspective** — 사용자가 본 재고가 저장 전에 바뀌었는지 감지하고, 바뀌었다면 반품 요청 전체를 중단한다.

## 구현 전에 풀 문제 {#challenges}

문제를 좁힌 뒤 구현 전에 확인할 범위도 분리했습니다.

- 음수 재고가 허용돼 오류가 남지 않는 요청의 처리 순서를 재현할 것
- POS 표시 수량과 다른 채널이 변경한 실제 재고를 같은 시간축에서 비교할 것
- Vue 화면이 최초 조회한 재고를 언제까지 유효한 값으로 볼지 정할 것
- 여러 상품 중 하나가 달라졌을 때 상품별 처리와 요청 전체 중단 중 정합성 단위를 정할 것
- 다른 재고 변경 경로를 모두 수정하지 않고 반품 흐름 안에서 감지할 지점을 찾을 것

## 기존 계약으로 변경 감지 {#response}

요청 객체에는 사용하지 않던 oldQty가 이미 있었습니다. 화면 진입 시 조회한 재고를 oldQty로 보관하고, 저장 직전에 서버가 다시 조회한 currentQty와 비교했습니다.

한 상품이라도 값이 다르면 요청 전체를 중단했습니다. 여러 상품을 함께 반품하는 화면에서 일부만 저장하면 사용자가 처리 결과를 다시 해석해야 하므로, 요청에 포함된 상품 묶음을 하나의 정합성 단위로 잡았습니다.

아래는 실제 구현이 아니라 처리 순서만 단순화한 예시입니다.

```text
현재 재고를 다시 조회한다

요청한 모든 상품의 oldQty와 currentQty를 비교한다
하나라도 다르면 전체 요청을 중단한다

모두 같으면 반품과 재고 증감을 반영한다
실패하면 전체 요청을 롤백한다
```

기존 필드를 조회 시점의 snapshot으로 활용했기 때문에 프론트엔드·백엔드 계약과 반품 흐름 안에서 변경을 끝낼 수 있었습니다. POS와 다른 재고 변경 경로까지 함께 수정하지 않았습니다.

## 강한 제어를 선택하지 않은 이유 {#choice}

상품별 조건부 UPDATE와 대상 행 잠금도 검토했습니다. 비교와 갱신을 원자적으로 묶을 수 있지만, 여러 상품의 잠금 순서와 대기 시간, 기존 재고 변경 경로에 미칠 영향까지 함께 다뤄야 했습니다.

팀장과 운영 패턴을 확인한 결과, 당시 반복된 문제는 완전히 같은 순간의 쓰기보다 화면을 오래 열어둔 동안 발생한 재고 변경이었습니다. 확인된 문제보다 보장 범위를 넓히지 않고, 기존 계약으로 변경을 감지하는 범위에서 마무리했습니다.

## 보장 범위 {#boundary}

저장 직전 수량이 화면 조회 당시 수량과 다르면 요청 전체를 중단합니다. 다만 SELECT로 비교한 뒤 별도 SQL로 갱신하므로, 비교 직후 발생하는 동시 변경까지 막지는 못합니다.

수량만 비교하기 때문에 10 → 8 → 10처럼 값이 바뀌었다가 돌아온 경우도 감지하지 못합니다. 완전한 동시 변경 감지가 필요해지면 조건부 UPDATE나 버전 값을 다시 검토해야 합니다. 이번 변경의 범위는 오래된 화면의 수량 차이를 감지하는 데까지였습니다.
